Software Engineering Design Documentation

1. Introduction

1.1 Purpose

This document explains the design of the Cricket Application, a flexible and well-organized system for handling cricket data. It keeps track of players, teams, matches, ball-by-ball events, and dismissals. The system is built using Microservices Architecture, which makes it easy to scale and manage. It uses modern technologies like Kafka for messaging, Celery for task management, and Docker for running services smoothly. The design ensures efficient data processing, real-time updates, and reliability. This application helps cricket fans, analysts, and teams access and manage match data easily while ensuring high performance and smooth operations across different services.

1.2 Scope

The application provides the following features:

  • Player and team management.

  • Match scheduling and tracking.

  • Ball-by-ball delivery tracking.

  • Real-time updates and notifications.

  • Analytics and statistics.

1.3 Target Audience

  • Developers

  • System Architects

  • QA Engineers

  • Product Managers

2. System Architecture

2.1 High-Level Architecture

The application follows a Microservices Architecture with the following components:

  1. API Gateway: Single entry point for all client requests.

  2. Microservices:

    • Player Service

    • Team Service

    • Match Service

    • Delivery Service

    • Dismissal Service

    • DismissalFielder Service

  3. Message Broker: Kafka for event streaming.

  4. Task Queue: Celery for background task processing.

  5. Database: PostgreSQL for structured data storage.

  6. Cache: Redis for caching frequently accessed data.

  7. Frontend: React for the user interface.

3. Microservices Design

3.1 Player Service

  • Responsibilities: Manage player data (CRUD operations).

  • Endpoints:

    • GET /players: Fetch all players.

    • POST /players: Add a new player.

    • GET /players/{id}: Fetch a specific player.

    • PUT /players/{id}: Update a player.

    • DELETE /players/{id}: Delete a player.

3.2 Team Service

  • Responsibilities: Manage team data (CRUD operations).

  • Endpoints:

    • GET /teams: Fetch all teams.

    • POST /teams: Add a new team.

    • GET /teams/{id}: Fetch a specific team.

    • PUT /teams/{id}: Update a team.

    • DELETE /teams/{id}: Delete a team.

3.3 Match Service

  • Responsibilities: Manage match data (CRUD operations).

  • Endpoints:

    • GET /matches: Fetch all matches.

    • POST /matches: Add a new match.

    • GET /matches/{id}: Fetch a specific match.

    • PUT /matches/{id}: Update a match.

    • DELETE /matches/{id}: Delete a match.

3.4 Delivery Service

  • Responsibilities: Manage ball-by-ball delivery data.

  • Endpoints:

    • GET /deliveries: Fetch all deliveries.

    • POST /deliveries: Add a new delivery.

    • GET /deliveries/{id}: Fetch a specific delivery.

    • PUT /deliveries/{id}: Update a delivery.

    • DELETE /deliveries/{id}: Delete a delivery.

3.5 Dismissal Service

  • Responsibilities: Manage dismissal data.

  • Endpoints:

    • GET /dismissals: Fetch all dismissals.

    • POST /dismissals: Add a new dismissal.

    • GET /dismissals/{id}: Fetch a specific dismissal.

    • PUT /dismissals/{id}: Update a dismissal.

    • DELETE /dismissals/{id}: Delete a dismissal.

3.6 DismissalFielder Service

  • Responsibilities: Manage fielder involvement in dismissals.

  • Endpoints:

    • GET /dismissalFielders: Fetch all fielders.

    • POST /dismissalFielders: Add a new fielder.

    • DELETE /dismissalFielders/{id}: Remove a fielder.

4. Event-Driven Workflow

4.1 Kafka Integration

  • Topics:

    • match_updates: For match-related events.

    • player_performance: For player performance events.

  • Producers: Publish events to Kafka topics.

  • Consumers: Listen for events and trigger Celery tasks.

4.2 Celery Integration

  • Tasks:

    • send_notification: Send notifications for match updates.

    • generate_report: Generate reports for matches.

  • Workers: Process tasks asynchronously.

5. Database Design

5.1 Tables

  • Players: player_id, player_name.

  • Teams: team_id, team_name.

  • Matches: match_id, match_date, venue, team1_id, team2_id.

  • Deliveries: delivery_id, match_id, inning, over, ball, batsman, non_striker, bowler, total_runs.

  • Dismissals: dismissal_id, delivery_id, dismissed_batsman, dismissal_type.

  • DismissalFielders: dismissal_fielder_id, dismissal_id, fielder.

5.2 Relationships

  • One-to-Many: Teams → Players, Matches → Deliveries.

  • Many-to-Many: Dismissals → Fielders.
